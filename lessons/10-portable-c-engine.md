# Lesson 10 — From `model.bin` to pixels in portable C

## Goal

Compile the same integer inference engine used by the firmware as an ordinary
desktop program, generate a raw RGB image, and prove that its bytes exactly
match a released reference image.

This lesson is divided into two small parts:

- **10A:** understand what the C program receives, executes, and produces;
- **10B:** install a desktop C compiler and perform the byte-exact test.

## 10A — The three different artifacts

The upstream source has been cloned into:

```text
upstream/pico-faces
```

At revision `ee15d9d`, the desktop test combines three things that serve
different purposes.

### 1. The inference engine

The reusable C source is in `engine/`:

```text
engine/src/graph.c        load the model and orchestrate generation
engine/src/dit.c          predict latent velocities
engine/src/vae_dec.c      decode the final latent into pixels
engine/src/kernels_ref.c  portable integer math operations
engine/src/prng.c         deterministic random-noise generator
```

This is the procedure—the code that knows *how* to run a model. It does not
contain the trained model's millions of individual parameter values.

### 2. The model blob

For the fast model:

```text
checkpoints/m3_long_cfg/model.bin
```

This binary blob contains the trained and quantized weights, biases,
requantization multipliers and shifts, lookup tables, folded conditioning
values, and other model data.

Think of the engine as a music player and `model.bin` as the recording. The
player contains the procedure; the recording contains the particular learned
content.

The companion file:

```text
checkpoints/m3_long_cfg/rf_cfg.h
```

contains compile-time geometry such as model width, depth, token count, latent
dimensions, and output dimensions. The engine checks that the blob's header
agrees with those compiled dimensions before using it.

### 3. The golden output

The released reference images are in:

```text
checkpoints/m3_long_cfg/goldens/golden_1.rgb
```

An `.rgb` file here is not a PNG. It is exactly this sequence of bytes:

```text
pixel 0 red, pixel 0 green, pixel 0 blue,
pixel 1 red, pixel 1 green, pixel 1 blue,
...
```

For a 128 × 128 RGB image, its expected size is:

```text
128 * 128 * 3 = 49,152 bytes
```

There is no header or compression. That makes direct comparison simple.

## The desktop test pipeline

```text
seed + step count
        |
        v
deterministic PRNG creates starting noise
        |
        v
portable C engine + model.bin
        |
        v
128 x 128 x 3 raw RGB bytes
        |
        v
compare with released golden RGB bytes
```

The desktop harness is `engine/desktop/main_golden.c`. It:

1. reads `model.bin`;
2. validates and maps its sections with `rf_model_load`;
3. derives the test condition and CFG setting from the seed;
4. calls `rf_generate`;
5. writes the resulting image bytes and intermediate latent taps; and
6. prints a CRC32 checksum.

## Why require a byte-exact match?

An image that merely *looks similar* might conceal a rounding, overflow,
weight-layout, or random-number error. Diffusion repeatedly feeds one result
into the next step, so a one-integer difference can propagate.

The test therefore compares every generated byte with the known output:

```text
generated byte 0 == golden byte 0
generated byte 1 == golden byte 1
...
generated byte 49151 == golden byte 49151
```

If all bytes agree, the desktop C implementation is executing this released
model deterministically according to the reference integer behavior.

This does not prove that every possible input is correct, but it is a much
stronger regression check than visual inspection.

## 10B — Compile and verify the engine

Zig 0.17 is installed and supplies a C99-compatible `zig cc` compiler. We use
it in place of the upstream GCC command; the C source files and model data are
unchanged.

From the `pico-faces-lab` directory, the repeatable verification command is:

```powershell
powershell -ExecutionPolicy Bypass -File .\lesson_10b_verify.ps1
```

The script performs four distinct operations:

1. **Compile:** translate the portable C source into
   `build/m3_long_cfg/rf_golden.exe`, using the fast model's `rf_cfg.h`.
2. **Load:** run that executable and load the released `model.bin`.
3. **Generate:** produce seed 1 with four Euler steps and write `eng_1.rgb`.
4. **Verify:** compare all output bytes and calculate both SHA-256 hashes.

Our verified result is:

```text
seed 1: crc32 b32e6e63
generated bytes: 49152
golden bytes:    49152
byte-exact:      True
SHA-256: F2B9AAC0661A9E5452D22829A82F7C6CF5CE6B971F4F1607ACFF48F1CE106222
```

The compiler translates source code into a Windows executable. It does not
train, quantize, or modify the model. The executable contains the engine
procedure and compile-time model geometry; the large learned parameter arrays
remain in `model.bin` and are loaded when the executable runs.

Matching SHA-256 hashes are another compact way to establish that the two
49,152-byte files are identical. If even one bit differed, their cryptographic
hashes would, with overwhelming probability, differ too.
